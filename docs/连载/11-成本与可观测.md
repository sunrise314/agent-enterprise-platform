# 11 成本与可观测：真实 token 不估算

> 第十一篇讲成本核算与可观测。企业交付里有一个常被忽视的硬需求：每一轮对话花了多少钱，要能对账。我是怎么做真实 token 采集和 p95 统计的。

## token 必须取真实值，不能估算

估算 token（按中文 1.5 token/字、英文 0.25 token/词）有两个问题：一是不准（不同模型 tokenizer 差异大），二是成本审计过不了——财务要的是精确到分的账单，不是大概数。

AgentScope 的 `Msg` 对象在模型返回后会自动携带 `usage` 字段：

```java
Msg result = agent.call(messages, ctx).block();
int tokenIn = result.getUsage().getPromptTokens();
int tokenOut = result.getUsage().getCompletionTokens();
```

实测一轮真实对话：`tokenIn=888, tokenOut=89`，来自模型返回的 usage 字段，精确到个。

## 旁路采集：不碰主链路

和评估、审计一样，token 采集走事件旁路。`AgentEventPublisher` 订阅 AgentScope 的事件流，每次 Agent 执行完毕就发出一个 `AgentEvent`，里面带上 token 用量、延迟、工具调用次数：

```java
// AgentEventPublisher 发出事件
AgentEvent e = AgentEvent.agentCompleted(agentName, sessionId,
    tokenIn, tokenOut, latencyMs, toolCalls, tenantId, userId);
publish(e);
```

三个订阅者各干各的：

| 订阅者 | 做什么 |
|---|---|
| `MetricsStore` | 聚合 calls、tokenTotal、p95 延迟，供 Prometheus 拉取 |
| `AuditLogger` | 审计行里带上 cost（按 token 单价计算） |
| `MetricCollector` | 实时更新 p95、token 均值、工具调用分布 |

## 指标体系

目前暴露了三类指标：

**调用量**：
- `agent_chat_calls_total`：累计对话次数
- `agent_tool_calls_total`：累计工具调用次数
- `agent_eval_runs_total`：累计评估次数

**成本**：
- `agent_token_input_total`：累计输入 token
- `agent_token_output_total`：累计输出 token
- `agent_cost_total`：累计成本（按模型单价计算）

**质量**：
- `agent_eval_pass_rate`：评估通过率
- `agent_eval_judge_hallucination_rate`：judge 检测幻觉率
- `agent_latency_p95_ms`：对话延迟 p95

Prometheus endpoint 是 `/api/metrics/prometheus`，Grafana 可以直接接。

## 实测数据

跑一轮完整评估（5 个用例 + 5 个 judge）：

| 指标 | 数值 |
|---|---|
| 总对话次数 | 10 |
| 总 token | 612 / 108（input / output） |
| 平均延迟 | 2340ms |
| p95 延迟 | 3013ms |
| 评估通过率 | 5/5 |
| judge 幻觉检出 | 1 条（规则断言漏掉的） |

所有数字都来自事件旁路采集，不是估算。

## 一个容易踩的坑

token 单价可能变（云厂商调价、换模型）。我的做法是单价从配置文件读：

```yaml
agent.llm.cost-per-1k-tokens: 0.002  # DeepSeek chat 约 ¥0.002/1K token
```

`MetricCollector` 每次聚合时从配置取单价计算成本，不用硬编码。改价只改配置，重启生效。
