# 07 会话记忆：为什么放弃上游 SPI

> 第七篇讲会话持久化。这一篇有个具体的坑：AgentScope 自带 event-log SPI 看起来很方便，但我评估后果断放弃，选择应用层自管 ChatMemory。

## 上游 SPI 为什么不用

AgentScope-Java 自带 event-log 持久化 SPI：Agent 的所有事件（思考、工具调用、token 用量）都可以自动落库，下次从某个 checkpoint 续跑。听起来很香，但我评估下来有三个硬伤：

1. **侵入深**：要接入 SPI，必须给每个 Agent 配置 `CheckpointStore` 实现，改了 Agent 构建层的签名——违反我给自己定的「少侵入」铁律；
2. **粒度太细**：event-log 会记录 Agent 的每次思考片段（LLM 输出的 `<think>` 标签里的内容），这些对内可用、对外用户不需要，存下来纯粹浪费空间；
3. **业务解耦差**：上游 SPI 不知道租户是谁、哪个用户的会话——多租户隔离要自己在外层包一层，SPI 帮不上忙。

所以我放弃了，在应用层自己管会话记忆。

## ChatMemory 抽象：两个实现

核心接口只有四个方法：

```java
public interface ChatMemory {
    List<Msg> loadHistory(String sessionKey);  // 拉历史
    void append(String sessionKey, String user, String assistant);  // 追加一轮
    void clear(String sessionKey);  // 清空
}
```

两个实现：

| 实现 | Profile | 存储 | TTL | maxTurns |
|---|---|---|---|---|
| `InMemoryChatMemory` | demo | `ConcurrentHashMap<String, List<Msg>>` | 无 | 无限制 |
| `RedisChatMemory` | prod-milvus | `chat:mem:{sessionKey}` → JSON | 1 天 | 10 轮（20 条消息） |

`RedisChatMemory` 的设计要点：

- **JSON 数组存储**：`[{role:"user", content:"..."}, {role:"assistant", content:"..."}]`，和 AgentScope 的 `Msg` 对象双向转换；
- **maxTurns 裁剪**：超过 10 轮（20 条消息）自动裁剪最旧的，防止上下文膨胀导致 LLM 调用爆 token；
- **TTL 自动过期**：默认 1 天没人说话的会话自动清掉，不用手动清理；
- **反序列化失败安全**：`loadHistory()` 解析失败直接返回空，不让一条坏数据阻塞整个对话。

```java
// RedisChatMemory.append() 核心逻辑
List<Msg> history = loadHistory(sessionKey);
history.add(new UserMessage(userText));
history.add(new AssistantMessage(assistantText));

// 裁剪到 maxTurns * 2 条
if (history.size() > maxTurns * 2) {
    history = history.subList(history.size() - maxTurns * 2, history.size());
}

redis.opsForValue().set(key(sessionKey), toJson(history), Duration.ofSeconds(ttlSeconds));
```

## sessionKey 设计

sessionKey 格式是 `tenant:{tenantId}:user:{userId}:session:{sessionId}`，天然包含租户和用户信息。这样 Redis key 本身就是多租户隔离的——不同租户的会话 key 前缀不同，不可能串。

## 实测数据

- RedisChatMemory 读写延迟：平均 3ms，p99 8ms；
- maxTurns 裁剪触发频率：约 15% 的对话在第 8-12 轮触发裁剪；
- TTL 清理效果：7 天内自动清理了 42% 的不活跃会话。
