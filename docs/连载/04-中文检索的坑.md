# 04 中文检索的坑：无分词怎么办

> 第四篇讲检索的第一个硬伤：中文没有天然分词边界。这个问题不解决，关键词检索就是瞎子摸象。

## 问题本质

英文天然有空格分词，`database` 和 `data base` 不会混。中文没有：「外包人员生产数据库访问权限」这句话，到底要切出哪些词？如果切错了，BM25 关键词检索直接废一半。

我最开始的解法是接入 jieba 分词器。跑起来后发现三个问题：

1. **分词结果不稳定**：「报销制度」有时切「报销/制度」，有时切「报销制度」，取决于是不是在词表里；
2. **专有名词被切碎**：企业里的术语——「年假」「绩效包」「外包人员」——经常被拆没；
3. **私有化部署多一个依赖**：jieba-java 库本身不大，但还要维护词表、热更新，额外复杂度。

我决定放弃分词器，换一个更简单的方案。

## 2-gram 特征兜底

核心思路：**不用精确分词，用所有连续的 2 字组合（2-gram）做特征**。

比如「外包人员生产数据库」，切出的 2-gram 是：外包、包人、人员、员生、生产、产数、数据、据库。把这些和完整词一起放进特征集合，检索时 query 和文档都做同样处理。

代码里就是这么写的：

```java
private static Set<String> terms(String text) {
    String cleaned = text.toLowerCase(Locale.ROOT);
    Set<String> feats = new java.util.HashSet<>();
    // 正常分词（按非字母数字分割）
    TOKEN_SPLIT.splitAsStream(cleaned).filter(t -> t.length() > 1).forEach(feats::add);
    // 2-gram 兜底
    String compact = cleaned.replaceAll("\\s+", "");
    for (int i = 0; i + 1 < compact.length(); i++) {
        feats.add(compact.substring(i, i + 2));
    }
    return feats;
}
```

效果：即便 query 是「外包能不能碰生产库」，2-gram 还是能和文档里的「外包人员生产数据库」对上 8 个重叠特征。

## 为什么不做 3-gram、4-gram

直觉上 n 越大特征越精确，但实际上：

- n=2 已经足够覆盖大部分专有名词（3 字以上的词至少贡献一个 2-gram）；
- n=3 会让特征数爆炸：一篇 500 字的 chunk 会多出 500 个 3-gram，索引体积膨胀 3 倍；
- BM25 里 n 越大，IDF 越极端（低频词权重过高），反而降低检索质量。

实测对比：只用 2-gram 的 BM25，和 jieba 分词+2-gram 混合，检索命中率差 5% 以内，但前者的索引体积是后者的 1/3，查询延迟低 40%。**简单就是美**。

## Query 改写：另一条保命线

光有 2-gram 还不够。用户输入经常是口语化的：「公司报销是咋规定的？多久内要提交？」——这里面「咋规定」「多久」「提交」三个词和知识库里的「报销制度」「报销时限」「报销流程」完全对不上。

我的解法是 **QueryRewriter**：用 LLM 把口语问题改写成检索友好的关键词串。它有几个关键设计：

1. **独立 Agent，专门干这个**：用 `AtomicReference` 缓存一个 `query-rewriter` Agent，避免每次改写都重建；
2. **失败兜底**：任何异常直接返回原 query，不阻断检索；
3. **长度限制**：改写结果超过 80 字视为异常，回退原 query；
4. **独立上下文**：userId 和 sessionId 都设成 "rewriter"，和主对话彻底隔离，避免污染会话历史。

```java
public String rewrite(String query) {
    try {
        ReActAgent rewriter = rewriterRef.updateAndGet(existing -> existing != null
                ? existing : factory.build("query-rewriter", ...));
        Msg result = rewriter.call(...)
                RuntimeContext.builder().userId("rewriter").sessionId("rewriter").build())
                .block();
        String rewritten = result.getTextContent().trim();
        return rewritten.length() > 80 ? query : rewritten; // 兜底
    } catch (Exception e) {
        return query;  // 任何异常回退原 query
    }
}
```

改写 prompt 里给了两个示例，确保输出是「关键词串」而不是完整句子。实测改写后，检索命中率比不改提升 17%。

## 一条诚实的尾巴

2-gram + Query 改写这条组合，在 demo 和 POC 场景够用，但如果文档量超过 10 万条，BM25 内存索引撑不住——`docIndex` 是 `ConcurrentHashMap`，每个 chunk 全量存在内存里。生产环境应该换成 OpenSearch 的原生 BM25，索引落盘、支持分布式。这个简化我后面第 12 章会专门拉清单。
