# 10 面试备考：AI 应用开发工程师（Agent 平台项目深挖）

> 目标岗位：诚迈 / 阿里 / 美团 / 携程 / 鼎捷 等 AI 应用开发岗。
> 素材来源：本项目（AgentScope-Java 二次开发的商用级企业智能体平台）全部**实机验证证据链**。
> 用法：`10.2` 是面试可直接背诵的量化证据；`10.3` 每模块分「口语版（30 秒回答）+ 六层认知（深挖）」。

## 10.1 项目电梯陈述（30 秒 / 60 秒）

**30 秒（口语）：**
> 我基于阿里 AgentScope-Java 开源框架做了二次开发，落地成一个**商用级、可私有化、源码可交付**的企业智能体平台。不是 demo——它把 RAG、多租户、RBAC 鉴权、审计、token 成本、评估、SSE 流式、可观测全部串起来了，而且每项都有真实调用验证。比如多租户隔离、JWT 权限拦截、LLM-as-judge 评估这几个，都是实机跑通的。

**60 秒（展开）：**
> 我做的这个平台核心是把 AgentScope-Java 从"框架能力"变成"能上线给企业用的产品"。具体我做了三件事：
> 一是**RAG 全链路**——文档解析（PDF/Word/TXT）、语义分块、增量 ingestion、Query 改写、多租户隔离检索、向量检索（Milvus 生产代码就绪）；
> 二是**企业级硬需求**——JWT 认证 + RBAC 接口级权限、审计留痕、token 真实采集、SSE 流式对话；
> 三是**质量闭环**——评测集自动跑分 + LLM-as-judge 语义复核 + 坏例自动沉淀，指标采集可对接 Grafana。
> 每一条都有量化验证，比如租户隔离测试、权限 403 拦截、token 从 0 占位改成真实值这些，都是我实机跑出来的。

## 10.3 六层认知：核心模块深挖

> 六层认知：**是什么 → 怎么做 → 为什么 → 坑/权衡 → 对比 → 原理延伸**。
> 面试时先说「口语版」把价值讲清；追问深度时走六层。

### 10.3.1 对话链路 + 会话持久化

**口语版：**
> 我用 AgentScope 的 ReActAgent 做对话，历史消息从记忆接口拉出来拼进去，实现跨轮上下文。记忆接口抽象成 ChatMemory，demo 用内存，生产换 Redis，对上层无感知。

**六层认知：**
1. **是什么**：Agent 对话要"记住"上文。我用 `ChatMemory` 接口 + `InMemoryChatMemory`(demo)/`RedisChatMemory`(生产)。
2. **怎么做**：`agent.call(List<Msg>, RuntimeContext).block()`，每次把 history + 新 query 组成消息列表喂给 Agent，完成后把本轮 user/assistant 写回记忆。
3. **为什么**：LLM 无状态，上下文必须显式传入。会话持久化让用户能多轮追问、Agent 能引用前文信息（如记住用户身份）。
4. **坑/权衡**：AgentScope 自带 event-log SPI 太复杂、侵入深，我放弃，改应用层自己管记忆，**少侵入上游、便于合新版本**。Redis 生产版 key 带租户前缀防跨租户串。
5. **对比**：应用层记忆 vs 框架 event-log：应用层可控、可加缓存/过期/TTL；event-log 精确但复杂。Token 消耗 vs 记忆长度：历史越长越贵，生产要截断/摘要。
6. **原理延伸**：消息数、长度、system prompt 的 token 预算；上下文窗口溢出策略（截断/滑动窗口/摘要压缩）；多轮中工具结果也进上下文。

### 10.3.2 RAG（召回 / 分块 / 改写 / 增量）

**口语版：**
> RAG 我走的是应用层模式：Agent 通过 kb_search 工具自主检索，检索结果带来源喂给模型作答。中文检索用 2-gram 特征解决没有分词的问题；生产用 Milvus 向量 + BM25 混合 + RRF 重排。文档解析、语义分块、增量 ingestion、Query 改写都做了。

**六层认知：**
1. **是什么**：检索增强生成。知识文档入库、检索、拼进 prompt，让 Agent 基于企业私有知识作答。
2. **怎么做**：`Retriever` 接口 + `InMemoryRetriever`(demo BM25)/`MilvusHybridRetriever`(生产)。kb_search 工具调 `RagService.searchSummary`，带租户过滤。ingestion：解析→语义分块→哈希去重→入库。
3. **为什么**：大模型不懂企业私有数据；RAG 用检索把知识注入，成本低、可更新、可溯源。
4. **坑/权衡**（重点）：
   - **中文无空格分词**：纯 token 精确匹配必失效 → 2-gram 特征（`年假政策→{年假,假政,政策}`）或接分词器；
   - **分块**：纯固定窗口切碎条款语义 → 段落感知 + 句子边界 + overlap；
   - **工具 description**：写不清"何时用/参数含义"，LLM 选错工具，召回准确率崩；
   - **Query 改写**：口语问题直接检索命中差，LLM 改写成"请假流程 申请 审批"式检索 query；
   - **增量**：重复上传污染检索空间，SHA-256 内容哈希去重 + 变更更新。
5. **对比**：BM25(关键词，快、可解释) vs 向量(语义，需 embedding 服务) vs 混合+RRF(取两者之长)。应用层 RAG vs 框架层 RAG（AgentScope 官方 ApplicationLayerRagExample 是应用层）。
6. **原理延伸**：embedding 模型选型（BGE 本地 / OpenAI 兼容）；向量维度与相似度度量（COSINE）；RRF 重排公式；召回 topK 与重排 topM；query 改写触发策略与成本。

### 10.3.3 多租户 + RBAC + JWT

**口语版：**
> 我做了接口级权限 + 多租户隔离。JWT 里带 userId/tenantId/role，AuthInterceptor 解析 token、按路径映射权限校验，过不了就 403，非法 token 401。租户上下文用响应式链路传，避免 ThreadLocal 跨线程丢。

**六层认知：**
1. **是什么**：认证（你是谁）+ 授权（你能干什么）+ 隔离（你只能看自己租户的数据）。
2. **怎么做**：`JwtUtil`(jjwt HS 签发/解析)→`AuthInterceptor` 解析 Bearer token→`AuthService` 路径→权限校验→注入 `TenantContext`。登录接口 `POST /api/auth/login` 签发 token。
3. **为什么**：企业平台多部门/多客户共用一套服务，必须角色控制 + 数据隔离，这是能"卖给企业"的前提。
4. **坑/权衡**（重点）：
   - **ThreadLocal 跨线程丢**：TenantContext 用 ThreadLocal 存，但 Reactor `boundedElastic` 线程读不到 → 改用 `RuntimeContext.put(TenantInfo.class,...)` 随响应式链路注入工具（非 @ToolParam 参数自动注入）；
   - **无 token 兜底**：demo 回退 header；生产强制 token；
   - **路径→权限映射**：`/api/agent→agent:chat`、`/api/eval→eval:run`、`/api/audit→audit:view`，粒度到接口。
5. **对比**：Spring Security @PreAuthorize vs 自研拦截器；RBAC vs ABAC（属性化）；JWT(无状态,便于水平扩展) vs Session(可撤销,服务端存)。
6. **原理延伸**：JWT 签名与防篡改；token 过期/刷新策略；权限到"工具级"（Agent 能调哪些工具）；租户隔离在向量库查询的过滤实现；超时/撤销（黑名单）。

### 10.3.4 审计 + token 成本

**口语版：**
> 我做了全链路审计：Agent 调用、工具调用都留痕，记录租户、用户、操作、耗时、token。token 用 `result.getUsage()` 真实采集，审计里能看到每次对话消耗多少 token，这是企业成本审计的关键。

**六层认知：**
1. **是什么**：谁在什么租户下做了什么、花了多少钱、成功没有，都要可查。
2. **怎么做**：`AuditLogger` 埋点 `agent.chat`(AgentServiceImpl) 与 `tool.kb_search`(BizTools)；`GET /api/audit` 查询。token 走 `Msg.getUsage()`→`ChatUsage.getInputTokens()/getOutputTokens()`。
3. **为什么**：合规 + 成本 + 排障。企业要能回答"这个 token 是谁烧的、哪次对话烧的"。
4. **坑/权衡**：审计不能阻塞主链路（旁路异步）；detail 字段长度截断；租户/用户从上下文可靠取到（不依赖 ThreadLocal）。
5. **对比**：内存环形缓冲(快,demo) vs 落库(持久,生产)。审计 vs 日志：审计是面向"合规/成本"的结构化记录，日志是面向"排障"的原始输出。
6. **原理延伸**：token 成本计价（input/output 单价不同、缓存 token）；审计与指标、评估的数据打通；生产审计落 PostgreSQL/ES + 导出。

### 10.3.5 评估（Runner + LLM-as-judge + 坏例沉淀）

**口语版（最有区分度）：**
> 评估我做了三层：一是关键词断言跑分，确定性判断答案覆盖关键点；二是 LLM-as-judge，用 DeepSeek 当裁判做语义/幻觉复核——它能发现关键词断言漏掉的编造；三是坏例自动沉淀，失败的 case 自动进回归集。这形成一个持续改进闭环。

**六层认知：**
1. **是什么**：自动化评测 Agent 回答质量，替代人肉逐条看。`POST /api/eval/run` 跑一套测试集 → 报告。
2. **怎么做**：`EvalCase`(question + expected/forbidden + assertion 模式) → `EvalRunService` 逐条调 Agent → `EvalJudge` 断言 + `LlmJudge`(DeepSeek 打分 `{score,hallucination,comment}`) → `MetricCollector` 聚合 → 坏例沉淀 `BadCaseRepository`。
3. **为什么**：Agent 输出非确定性，改一个 prompt/模型可能悄悄变差，必须有自动回归。
4. **坑/权衡**（重点）：
   - **中文措辞多样**："30 天内" vs "30天"，断言要选**稳健子串**（如"30"）；
   - **空期望恒失败**：缺失识别必须显式用 `contains_any`；
   - **LLM-judge 偏见/不稳定**：固定 judge 模型 + prompt 保证相对可对比；输出 JSON 容错解析（找首尾 `{}`）；
   - **判幻觉的价值**：p-002 关键词断言通过，但 judge 识别"编造差旅标准"打分 4——双层评估能发现单断言漏掉的语义问题。
5. **对比**：关键词断言(确定、快、漏语义) vs LLM-judge(懂语义、慢/贵/有偏见)。自动化断言 vs 黄金答案比对 vs LLM 评估。
6. **原理延伸**：评估指标定义（完成率/幻觉率/P95/token）；测试集设计（positive/boundary/adversarial）；坏例→人工审核→回归集闭环；评估与 CI/CD 集成（发版前 gate）。

### 10.3.6 SSE 流式对话

**口语版：**
> 流式我用 AgentScope 的 `streamEvents` 拿事件流，映射到 SSE：文本增量推 delta、工具调用推 tool、完成推 done。前端能边生成边展示，体验好很多。

**六层认知：**
1. **是什么**：SSE（Server-Sent Events）单向服务端推送，让 LLM 输出边生成边到前端。
2. **怎么做**：`POST /api/agent/chat/stream` 建 `SseEmitter` → `AgentServiceImpl.streamChat` 订阅 `agent.streamEvents(msgs, ctx)`(返回 `Flux<AgentEvent>`) → `TextBlockDeltaEvent.getDelta()→delta`、`ToolCallStartEvent.getToolCallName()→tool`、`AgentResultEvent→usage`、完成→`done`。
3. **为什么**：非流式要等 5-10 秒无响应，用户感知"卡死"；流式第一 token 秒出，体验质变。也支撑工具调用过程可视化。
4. **坑/权衡**：
   - 事件类型要精确映射（delta/tool/done），不要漏事件或重复；
   - 完成时统一收尾：保存记忆 + 审计 + token（不能丢在订阅回调外）；
   - 客户端断开要容错（send 抛异常 catch）；
   - **依赖增多后命令行超长**：Windows `CreateProcess error=206` → 改 `java -jar` 启动（classpath 走 manifest）。
5. **对比**：SSE vs WebSocket（SSE 单向、HTTP 友好、自动重连；WebSocket 双向）。`streamEvents`(事件级) vs `call`(聚合结果)。
6. **原理延伸**：Reactor `Flux` 背压；SseEmitter 超时/心跳；流式下如何统计 token 与审计；与前端 EventSource 对接。

### 10.3.7 指标采集 + 可观测

**口语版：**
> 指标我复用了 Agent 事件流，旁路异步采集成 token、调用数、P95 延迟，提供 summary/series 查询接口，能对接 Grafana。关键点是旁路不阻塞主链路。

**六层认知：**
1. **是什么**：把 Agent 调用量化成可监控指标：调用数、token、延迟、失败率。
2. **怎么做**：`MetricsSubscriber` 实现 `AgentEventListener` 注册到 `AgentEventPublisher`，订阅 `llmCall/agentFinished/agentFailed/toolResult` → `MetricsStore`（demo 内存按分钟聚合；生产 InfluxDB/PostgreSQL）。`GET /api/metrics/summary` + `/series`。
3. **为什么**：企业要监控成本（token）与稳定性（P95/错误率），出问题能定位、上 Grafana 能看板。
4. **坑/权衡**：旁路异步避免阻塞主链路；存储抽象隔离 demo/生产；token 成本是企业的核心关注点。
5. **对比**：Prometheus(拉取) vs Telegraf+InfluxDB(推)；事件旁路 vs 埋点侵入。指标 vs 审计 vs 日志三种数据流分工。
6. **原理延伸**：指标口径（P95 计算）；时序存储选型；告警阈值设计（延迟突增/错误率/工具失败率）；与 LLM 配额/限流联动。

### 10.3.8 Milvus 向量检索（生产就绪）

**口语版：**
> 向量检索我写了生产实现 MilvusHybridRetriever，用 Milvus Java SDK v2 API，向量 + BM25 混合 + RRF 重排，按租户过滤。代码编译通过、生产就绪；本机没有 Milvus/Docker 环境，实机验证待环境。（诚实）

**六层认知：**
1. **是什么**：语义向量检索，理解"意思相近"而非字面相同。生产方案用 Milvus 存向量。
2. **怎么做**：`EmbeddingService` 向量化（OpenAiEmbeddingService 可指向本地 BGE）→ `CreateCollectionReq`(dimension/primaryField/metricType=COSINE) → `InsertReq`(gson JsonObject, FloatVec) → `SearchReq`(FloatVec, topK)。
3. **为什么**：BM25 只认关键词，用户说"想休几天假"可能匹配不上"年假"；向量能抓语义。
4. **坑/权衡**：
   - SDK 版本 API 差异大：v1 编译失败，`javap` 反编译 jar 确认 v2 API（`MilvusClientV2`、`FloatVec`、gson JsonObject）；
   - 需要 embedding 服务（本地 BGE/Xinference/Ollama）+ Milvus 实例，环境较重；
   - 纯向量可能召回噪音，混合 + RRF 更稳。
5. **对比**：Milvus vs Chroma（规模/分布）；BM25 vs 向量 vs 混合+RRF。Milvus v1 vs v2 API。
6. **原理延伸**：embedding 模型选型；向量维度/索引类型（HNSW）；相似度度量（COSINE/内积）；RRF 公式；向量+关键词分数归一化。

## 10.4 面试官高频追问 & 标准应答（口语版）

**Q1：这个项目是你独立做的吗？工作量和真实性？**
> 核心设计、编码、验证都是我独立完成的。基于 AgentScope-Java 开源框架做二次开发，重点在工程化和商用化：少侵入上游、扩展/SPI、可合并新版本。每个模块都有我实机验证的证据，比如租户隔离、403/401、token 真实值，都能现场演示。

**Q2：为什么用 AgentScope-Java 而不是自研或 LangChain/LangGraph？**
> 自研代价高；AgentScope 是阿里开源、Java 生态、生产级（事件流、工具、多 Agent）。和 LangChain(偏 Python)比，我在 Java 技术栈做企业服务，AgentScope 更契合。关键是我没被框架绑死——记忆、检索、鉴权都在应用层自己做，框架只提供 Agent 执行内核。

**Q3：多租户怎么做到数据真正隔离？**
> 三层：检索过滤（检索器按 tenantId 过滤）、上下文注入（RuntimeContext 带 TenantInfo 沿响应式链路传）、接口鉴权（JWT 里 tenantId + RBAC 校验）。我用两个租户实测：tenant-0 能查到年假、tenant-1 查不到，验证了隔离。关键坑是 ThreadLocal 跨线程会丢，所以用响应式上下文传。

**Q4：怎么防止 Agent 幻觉 / 保证回答可信？**
> 三层防线：一是 RAG 带来源，检索不到就让它如实说"知识库暂无"（对抗用例验证）；二是评估有 not_contains 断言 + LLM-as-judge 幻觉复核，编造会被判出来并沉淀坏例；三是审计留痕可回溯。实测：a-002 编造食堂菜单被命中 forbidden 判失败并进坏例库。

**Q5：token 成本怎么控制？**
> 先可量化：每轮对话真实 token 入库（审计 + 指标），能看到钱烧在哪。再优化：Query 改写控制检索质量、记忆截断/摘要控历史长度、评估选低分模型/缓存。企业关心成本，token 采集是第一步，没量化就没法优化。

**Q6：为什么评估用关键词断言还要 LLM-judge？**
> 两层互补。关键词断言快、确定、可解释，但漏语义等价——"30 天内"和"30天"措辞不同可能误判。LLM-judge 懂语义，能发现断言漏掉的编造：实测 p-002 断言过了、judge 识别它"编造了差旅标准"打分 4。但 judge 慢、贵、有偏见，所以固定模型 + 相对参考，不做绝对真值。

**Q7：这个平台能卖给企业吗？还缺什么？**
> 架构和核心能力是商用级的：JWT+RBAC、多租户、审计、token 成本、评估闭环、流式、可观测，都实机验证。当前 Milvus 向量、Redis 会话是生产代码就绪、待实机验证。真上线还差：Milvus/Redis/PostgreSQL 环境部署、监控告警接入 Grafana、CI/CD 发版 gate、安全加固（限流/防注入）、运维文档。这是工程推进计划，不是架构缺陷。
